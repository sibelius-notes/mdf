# Chapter 1: Computer Networks and the Internet

## 1.1 What is the Internet?

The Internet can be understood from two complementary perspectives: a **nuts-and-bolts view** that describes the concrete hardware and software components, and a **service view** that describes the Internet as an infrastructure providing services to distributed applications.

From the nuts-and-bolts perspective, the Internet is a collection of billions of connected computing devices — called **hosts** or **end systems** — running network applications. End systems are connected by a network of **communication links** and **packet switches**. Links are made of different physical media: coaxial cable, copper wire, optical fiber, and radio spectrum, each with a characteristic **transmission rate** measured in bits per second (bps). When one end system sends data to another, it segments the data and adds header bytes to each segment, forming **packets**. These packets are forwarded through the network and reassembled at the destination.

**Packet switches** forward arriving packets onward toward their ultimate destination. The two most prevalent types are **routers** (in the network core) and **link-layer switches** (in access networks). The sequence of communication links and packet switches traversed by a packet is called a **route** or **path** through the network.

From the service view, the Internet is an infrastructure that provides services to distributed applications such as Web browsing, streaming video, email, social media, and online games. These applications are said to be **distributed** because they involve multiple end systems exchanging data. End systems attached to the Internet provide a **socket interface** — a set of rules by which an application program running on one end system can ask the Internet to deliver data to a specific destination program running on another end system.

A **protocol** defines the format and the order of messages exchanged between two or more communicating entities, as well as the actions taken on the transmission or receipt of a message or other event. Protocols are central to everything in the Internet. The **Transmission Control Protocol (TCP)** and the **Internet Protocol (IP)** are the two most important Internet protocols. IP specifies the format of the packets sent and received among routers and end systems. The principal protocols are collectively known as **TCP/IP**.

## 1.2 The Network Edge

The **network edge** refers to the end systems themselves and the **access networks** that connect them to the first router (called the **edge router**) on a path into the Internet.

**Digital Subscriber Line (DSL)** uses the existing telephone infrastructure. The home's DSL modem takes digital data and translates it to high-frequency tones for transmission over telephone wires to the telephone company's **central office (CO)**, where a **DSLAM** demultiplexes the data and phone signals. DSL is designed for asymmetric use: downstream transmission rates are higher than upstream rates. Typical downstream rates are 24 Mbps, upstream 2.5 Mbps; newer standards (VDSL2) achieve hundreds of Mbps.

**Cable Internet access** uses the existing cable television infrastructure. Because both fiber and coaxial cable are employed, cable Internet access is often called **hybrid fiber coax (HFC)**. Cable Internet access requires special modems called **cable modems**. At the cable head end, the **cable modem termination system (CMTS)** performs a similar function to DSL's DSLAM. A key characteristic of cable Internet access is that it is a **shared broadcast medium**: every packet sent by the head end travels downstream on every link to every home, and every upstream packet travels toward the head end. This shared nature means that if several users are simultaneously downloading a video file, each user will receive a lower downstream rate than if only one user is active.

**Fiber to the Home (FTTH)** provides an optical fiber path from the CO directly to the home. The two competing optical distribution network technologies are **active optical networks (AONs)** and **passive optical networks (PONs)**. In PON distribution, each home has an **optical network terminator (ONT)**, connected by dedicated optical fiber to a neighborhood **splitter** that combines signals for a single shared optical fiber to the CO's **optical line terminator (OLT)**.

In **enterprise and home access**, **Ethernet** uses twisted-pair copper wire and provides rates of 100 Mbps, 1 Gbps, or 10 Gbps to end systems. **WiFi** (IEEE 802.11) gives wireless users transmission rates of tens to hundreds of Mbps within a radius of a few tens of meters from a **wireless access point (AP)** connected to the wired enterprise network.

**Wide-area wireless access** technologies such as **3G**, **LTE (4G)**, and **5G** allow users to send and receive data anywhere within range of a base station. Whereas WiFi uses unlicensed spectrum, cellular wireless uses licensed spectrum, with rates of many tens of Mbps for LTE and 4G.

Physical media can be broadly categorized as **guided media** (waves propagate in a solid medium, e.g., fiber optic cable, twisted-pair copper wire, coaxial cable) or **unguided media** (waves propagate in the atmosphere and outer space, e.g., radio, satellite).

## 1.3 The Network Core

The network core is the mesh of packet switches and links that interconnects the Internet's end systems.

**Packet switching** is the dominant approach. To send a message from source to destination, the source breaks long messages into smaller chunks of data known as **packets**. Packets are transmitted at the full rate of the link, and most packet switches use **store-and-forward transmission**: the switch must receive the entire packet before it can begin to transmit the first bit of the packet onto the outbound link. The total delay to transmit a single packet of \(L\) bits over a path of \(N\) links each of rate \(R\) bps is:

\[d_{\text{end-to-end}} = \frac{NL}{R}\]

Each packet switch has multiple links attached to it, and for each attached link the switch has an **output buffer** (also called an **output queue**). Packets can suffer from **queuing delays** when the buffer is occupied with other packets, and if the buffer is completely full, **packet loss** occurs — either the arriving packet or an already-queued packet will be dropped.

Routers use **forwarding tables** to determine which output link to send a packet on. The Internet has a number of special routing protocols that are used to automatically set the forwarding tables.

**Circuit switching** is an alternative approach used in traditional telephone networks. In circuit-switched networks, the resources needed along a path (buffers, link transmission rate) are **reserved** for the duration of the communication session. Circuit switching can use **frequency-division multiplexing (FDM)**, where the frequency spectrum of a link is divided into frequency bands, or **time-division multiplexing (TDM)**, where time is divided into frames of fixed duration, each frame divided into fixed-number slots.

The key difference: circuit switching guarantees a constant rate, while packet switching allows more users to use the network simultaneously by statistical multiplexing, though it may experience variable delay and packet loss.

A **network of networks**: end systems connect to the Internet via **access ISPs**. These access ISPs themselves must be interconnected so that any two hosts in the world can send packets to each other. This interconnection is achieved through a hierarchy of **regional ISPs**, **tier-1 ISPs**, **Internet Exchange Points (IXPs)**, and **content provider networks** (like Google's private backbone), all peering to exchange traffic without settlement, with lower-tier ISPs paying higher-tier providers.

## 1.4 Delay, Loss, and Throughput in Packet-Switched Networks

A packet can be delayed by four sources as it travels from one node (router or end system) to a subsequent node along the path.

**Processing delay** \(d_{\text{proc}}\): the time required to examine the packet's header and determine where to direct it, typically microseconds or less.

**Queuing delay** \(d_{\text{queue}}\): the time a packet waits at the queue before it can be transmitted, ranging from microseconds to milliseconds. If \(a\) is the average packet arrival rate (packets/sec) and \(R\) is the link rate (bits/sec) and \(L\) is the packet length (bits), then the **traffic intensity** is \(La/R\). When \(La/R \approx 1\), the average queuing delay grows rapidly; when \(La/R > 1\), the queue grows without bound.

**Transmission delay** \(d_{\text{trans}}\): the time to push all the packet's bits onto the link. For a packet of \(L\) bits on a link with transmission rate \(R\) bps: \(d_{\text{trans}} = L/R\).

**Propagation delay** \(d_{\text{prop}}\): the time for a bit to propagate from the beginning of the link to the next router. The propagation speed depends on the physical medium. For a link of physical distance \(d\) with propagation speed \(s\): \(d_{\text{prop}} = d/s\).

The total **nodal delay** is:
\[d_{\text{nodal}} = d_{\text{proc}} + d_{\text{queue}} + d_{\text{trans}} + d_{\text{prop}}\]

**Throughput** is the rate (bits/time unit) at which bits are transferred between sender and receiver. The **instantaneous throughput** is the rate at any instant; the **average throughput** over an entire file transfer of \(F\) bits taking \(T\) seconds is \(F/T\). For a file transfer through a two-link path with rates \(R_s\) and \(R_c\), the throughput is \(\min(R_s, R_c)\). The link on the path with minimum transmission rate is the **bottleneck link**.

## 1.5 Protocol Layers and Service Models

To provide structure to the design of network protocols, the protocols are organized in **layers**. The **five-layer Internet protocol stack** consists of:

1. **Application layer**: supports network applications (HTTP, SMTP, FTP, DNS). Application-layer packets are called **messages**.
2. **Transport layer**: transports application-layer messages between application endpoints (TCP, UDP). Transport-layer packets are called **segments**.
3. **Network layer**: moves network-layer packets (called **datagrams**) from one host to another (IP, routing protocols).
4. **Link layer**: moves **frames** from one network element to an adjacent one along a route (Ethernet, WiFi, PPP).
5. **Physical layer**: moves the individual bits within a frame from one node to the next using physical media.

The alternative **7-layer OSI model** adds a **presentation layer** (for data interpretation services like encryption, compression) and a **session layer** (for delimiting and synchronization of data exchange) between the application and transport layers.

**Encapsulation**: at each layer, a protocol adds its own header information to the payload from the layer above. At the sending host, data passes down from application through transport (adding segment header) through network (adding datagram header) through link (adding frame header and trailer). At routers, the link and network layers are processed and re-encapsulated. At the receiving host, the headers are stripped at each layer on the way up. This process is called **encapsulation**.

## 1.6 Networks Under Attack

**Malware** can be delivered by **viruses** (user interaction required) or **worms** (self-replicating without explicit user interaction). A **botnet** is a network of compromised devices controlled by an attacker.

A **denial-of-service (DoS) attack** renders a network, host, or infrastructure unusable by legitimate users. A **distributed DoS (DDoS)** attack exploits a botnet to overwhelm a target with traffic from many hosts. Three classes: vulnerability attacks (exploit protocol bugs), bandwidth flooding (sending a deluge of packets), and connection flooding (establishing many half-open TCP connections).

**Packet sniffing**: a passive receiver in the vicinity of a wireless transmitter can record a copy of every packet transmitted — a **packet sniffer**. Since sniffers are passive, they are difficult to detect.

**IP spoofing**: injecting packets with a false source address. The receiver cannot easily determine if the source address is genuine. End-point authentication (verifying that the entity is who it claims to be) solves the problem.

## 1.7 History of Computer Networking and the Internet

The development of packet switching in the early 1960s by Leonard Kleinrock, Paul Baran, and Donald Davies laid the theoretical groundwork. The **ARPANET** (funded by DARPA) connected four university sites in 1969 and grew rapidly. In the late 1970s, Vint Cerf and Bob Kahn developed the TCP/IP architecture. The **NSFNET** in the 1980s connected universities and became the backbone for academic Internet traffic. The World Wide Web, invented by Tim Berners-Lee at CERN around 1989–1991, provided an easy-to-use application platform that drove explosive commercialization through the 1990s and into the present era of pervasive Internet access.

# Chapter 2: Application Layer

## 2.1 Principles of Network Applications

Network applications are programs that run on end systems and communicate over the network. In the **client-server architecture**, there is an always-on host, called the **server**, which services requests from many other hosts, called **clients**. Clients do not communicate directly with each other; all communication passes through the server. Web, email, FTP, and DNS use client-server architecture. In **peer-to-peer (P2P) architecture**, there is minimal or no reliance on a dedicated server. Pairs of hosts, called **peers**, communicate directly.

A **process** is a program running within an end system. Processes on two different end systems communicate by exchanging **messages** across the computer network. The process that initiates communication is labeled the **client**; the process that waits to be contacted is the **server**. A **socket** is the interface between the application layer and the transport layer within a host, analogous to a door through which a process can send and receive messages.

To receive messages, a process must have an **address**. An Internet host is identified by its **IP address** (32-bit quantity uniquely identifying the host). The destination **port number** identifies the receiving process (socket) within the host.

The transport layer provides services to the application: **reliable data transfer** (guaranteeing that data sent will arrive correctly and completely), **throughput** guarantees, **timing** guarantees, and **security** (encryption). TCP provides reliable, in-order data delivery, flow control, and congestion control. UDP provides unreliable, unordered delivery with no flow or congestion control. Applications requiring low-delay (e.g., telephony, online gaming) often prefer UDP.

## 2.2 Web and HTTP

The **World Wide Web** uses the **HyperText Transfer Protocol (HTTP)**. A **Web page** consists of objects, each of which can be an HTML file, a JPEG image, a Java applet, and so on, each addressable by a **URL**. HTTP is a client-server application-layer protocol. It is implemented on two programs: a **client** program (browser) and a **server** program. HTTP uses TCP as its underlying transport.

HTTP is **stateless**: the server maintains no information about past client requests. The protocol operates in **request-response** fashion.

In **non-persistent HTTP** (HTTP/1.0), each TCP connection carries at most one request/response pair, then the connection is closed. To fetch a base HTML file and its ten JPEG images requires eleven TCP connections. Each connection incurs a **two round-trip time (RTT)** overhead (one RTT for TCP handshake, one for HTTP request/response).

In **persistent HTTP** (HTTP/1.1 default), the server leaves the TCP connection open after sending a response. Multiple requests can be sent **back-to-back** (pipelining) without waiting for replies to pending requests.

**RTT** is the time it takes for a small packet to travel from the client to the server and back. For non-persistent HTTP, the response time per object is: 2 RTT + transmission time of the object.

An HTTP **request message** has the form:

```
GET /somedir/page.html HTTP/1.1
Host: www.someschool.edu
Connection: close
User-agent: Mozilla/5.0
Accept-language: fr
```

The first line is the **request line** (method, URL, HTTP version). Subsequent lines are **header lines**. Methods include GET, POST, HEAD, PUT, DELETE.

An HTTP **response message** has a **status line** (version, status code, phrase), header lines, and an entity body. Key status codes: `200 OK`, `301 Moved Permanently`, `400 Bad Request`, `404 Not Found`, `505 HTTP Version Not Supported`.

**Cookies** allow sites to keep track of users. Four components: (1) a cookie header line in the HTTP response, (2) a cookie header line in subsequent HTTP requests, (3) a cookie file kept on the end system, (4) a back-end database at the web site.

A **web cache** (also called a **proxy server**) satisfies HTTP requests on behalf of an origin Web server. The browser is configured to send HTTP requests to the web cache. If the cache has the requested object, it returns the object; otherwise it requests it from the origin server. Web caches reduce response time and reduce traffic on an institution's access link. A **conditional GET** (using `If-Modified-Since:` header) allows the cache to verify whether its cached object is still up to date.

**HTTP/2** reduces latency by enabling **multiplexing** of multiple requests and responses over a single TCP connection, adding **server push** (server can send resources the client hasn't yet requested), **header compression**, and **request prioritization** through binary framing. A key problem with HTTP/1.1 over multiple connections is **HOL (Head-of-Line) blocking** where a large object blocks smaller objects behind it in a queue; HTTP/2's framing breaks messages into frames that are interleaved.

## 2.3 Electronic Mail in the Internet

Electronic mail uses three major components: **user agents**, **mail servers**, and the **Simple Mail Transfer Protocol (SMTP)**. A user agent allows the user to compose, read, and forward messages. Mail servers form the core of the e-mail infrastructure; each user has a **mailbox** in a mail server. **SMTP** transfers messages between mail servers. SMTP is a push protocol (the sending mail server pushes the file to the receiving server) that uses TCP.

SMTP is an older protocol constrained to 7-bit ASCII. SMTP uses **persistent connections** and uses commands: HELO, MAIL FROM, RCPT TO, DATA, QUIT.

**POP3 (Post Office Protocol version 3)** is a simple mail access protocol with three phases: authorization, transaction (download messages, mark for deletion), update. **IMAP (Internet Mail Access Protocol)** keeps all messages on the server and allows the user to create and manage folders. IMAP is more complex than POP3 but lets the user access messages from multiple devices.

**MIME (Multipurpose Internet Mail Extensions)** extends SMTP to allow non-ASCII data (binary files, images) in email by adding content-type and content-transfer-encoding headers.

## 2.4 DNS — The Internet's Directory Service

The **Domain Name System (DNS)** provides the service of mapping human-friendly **hostnames** (e.g., `www.yahoo.com`) to machine-readable **IP addresses**. DNS is a distributed database implemented in a hierarchy of **DNS servers**, and an application-layer protocol that allows hosts to query the distributed database. DNS adds delay but results are usually cached.

DNS provides several other services: **host aliasing** (canonical vs. alias hostnames), **mail server aliasing**, and **load distribution** (rotating among a set of IP addresses for a single hostname).

The DNS servers are organized in a three-level hierarchy: **root DNS servers** (13 in the world, each replicated many times), **top-level domain (TLD) DNS servers** (for .com, .org, .net, country domains), and **authoritative DNS servers** (an organization's own DNS servers providing authoritative hostname-to-IP mappings).

A **local DNS server** (default name server) is provided by an ISP. When a host makes a DNS query, the query is sent to the local DNS server which acts as a proxy forwarding the query into the hierarchy.

In **iterative query resolution**, the contacted server replies with a referral to another DNS server. In **recursive query resolution**, the contacted server obtains the mapping on behalf of the requester. Iterative is most common.

**DNS caching** improves performance: once a name server learns a mapping, it caches the mapping. TLD server addresses are often cached in local DNS servers, allowing root DNS servers to be bypassed. Cached entries have a **time-to-live (TTL)** after which they expire.

DNS stores information in **resource records (RRs)** — four-tuples `(Name, Value, Type, TTL)`:

| Type | Name | Value |
|------|------|-------|
| A | hostname | IPv4 address |
| NS | domain | hostname of authoritative DNS server |
| CNAME | alias hostname | canonical hostname |
| MX | domain | canonical name of mail server |

DNS messages (both query and reply) have the same format: a 12-byte header (identifier, flags, number of questions/answers/authority/additional RRs), question section, answer section, authority section, and additional section. DNS uses UDP with port 53 (TCP for zone transfers).

## 2.5 Peer-to-Peer File Distribution

In **P2P file distribution**, peers directly exchange file chunks with each other. The distribution time grows linearly with the number of peers in the client-server model, but in P2P it is nearly self-scaling: each arriving peer brings upload capacity.

For the distribution time in **client-server**:
\[D_{CS} \geq \max\left(\frac{NF}{u_s},\; \frac{F}{d_{\min}}\right)\]
where \(F\) is the file size, \(N\) is the number of peers, \(u_s\) is the server upload rate, and \(d_{\min}\) is the minimum client download rate.

For P2P:
\[D_{P2P} \geq \max\left(\frac{F}{u_s},\; \frac{F}{d_{\min}},\; \frac{NF}{u_s + \sum u_i}\right)\]

**BitTorrent** is a popular P2P file distribution protocol. The collection of all peers participating in the distribution of a file is called a **torrent**. Peers in a torrent download equal-size **chunks** of the file (typically 256 kbytes). A **tracker** keeps track of peers participating in a torrent. When a new peer joins, it registers with the tracker and periodically informs the tracker it is still in the torrent. The tracker sends the new peer a list of a subset of participating peers, and the new peer attempts TCP connections to all of them — these connected peers are its **neighboring peers**.

A peer requesting chunks uses **rarest first**: request the chunks that have the fewest copies among the neighbors, to equalize the rarity distribution. For sending chunks, BitTorrent uses a **tit-for-tat** mechanism: each peer prioritizes the four neighbors currently supplying it data at the highest rate (the **unchoked** peers), re-evaluated every 10 seconds. Every 30 seconds, a peer randomly selects an additional neighbor and starts sending chunks — **optimistic unchoking** — enabling discovery of better trading partners.

## 2.6 Video Streaming and Content Distribution Networks

Video streaming represents the majority of Internet traffic. **Streaming stored video** involves encoding the video at a server, transmitting it over the network, and playing it at the client. Continuous playout from a **client-side application buffer** handles variable network delay (buffering). **Prefetching** allows the client to store more video in the buffer than the current consumption point.

**DASH (Dynamic Adaptive Streaming over HTTP)** divides video into **chunks** encoded at different bit rates. A **manifest file** lists the URLs of chunks at each bit rate. The client periodically estimates the download bandwidth and selects the appropriate bit rate chunk to request, adapting to changing network conditions.

**Content Distribution Networks (CDNs)** address the challenge of streaming video to geographically dispersed users. A CDN manages servers in multiple geographically distributed locations, stores copies of videos and other content in its servers, and attempts to direct each user request to a CDN location that will provide the best experience. CDNs use two server placement philosophies: **Enter Deep** (deploy servers inside access ISPs, close to end users, low delay) and **Bring Home** (fewer large clusters at key locations in IXPs, easier to maintain).

**Intercepting** user requests is done via **DNS** redirection: when the user requests a video, the hostname in the URL maps to the CDN's authoritative DNS, which returns an IP address of a CDN server selected to serve the user.

## 2.7 Socket Programming

The **socket API** allows applications to send and receive data. A socket is identified by the host's IP address and a port number.

**UDP socket programming**: the client creates a UDP socket, sends datagrams to a specific (address, port) pair with `sendto()`, and receives with `recvfrom()`. Each datagram includes destination address.

**TCP socket programming**: the server creates a **welcoming socket** (also called **server socket**) and calls `accept()`, which blocks until a client connects. The client creates a socket and calls `connect()`, completing a TCP 3-way handshake. `accept()` returns a new **connection socket** for the specific client. Data is sent and received through this connection socket using `send()`/`recv()`.

# Chapter 3: Transport Layer

## 3.1 Introduction and Transport-Layer Services

The transport layer provides **logical communication** between application processes running on different hosts. A transport-layer protocol is implemented in the end systems but not in network routers. On the sending side, the transport layer converts application-layer messages into transport-layer **segments** by breaking messages into smaller chunks and adding a transport-layer header. On the receiving side, segments are assembled and passed to the application layer.

The relationship between transport and network layers: while the transport layer provides logical communication between **processes**, the network layer provides logical communication between **hosts**. Transport-layer protocols operate only in the end systems.

**Multiplexing and demultiplexing**: at the transport layer, the process of gathering data chunks from different sockets, encapsulating each data chunk with header information to create segments, and passing the segments to the network layer is called **multiplexing**. The job of delivering the data in a transport-layer segment to the correct socket is called **demultiplexing**. Each socket has a unique identifier. A segment has source and destination port number fields in the header. Port numbers range from 0 to 65535; **well-known port numbers** are 0–1023, reserved for specific protocols (HTTP=80, FTP=21, SMTP=25, DNS=53).

**Connectionless demultiplexing (UDP)**: a UDP socket is identified by a destination IP address and destination port number. Two UDP segments with the same destination IP and port are directed to the same socket regardless of source.

**Connection-oriented demultiplexing (TCP)**: a TCP socket is identified by a four-tuple (source IP, source port, destination IP, destination port). Different TCP segments with different source IP or source port are directed to different sockets.

## 3.2 Connectionless Transport: UDP

**UDP (User Datagram Protocol)** adds almost nothing to IP beyond multiplexing/demultiplexing and error checking. A UDP segment consists of a header with four fields: source port (2 bytes), destination port (2 bytes), length (2 bytes, in bytes of segment including header), and **checksum** (2 bytes), followed by the application data.

The **UDP checksum** provides error detection. The sender performs the 1s-complement sum of all 16-bit words in the segment and stores the result in the checksum field. At the receiver, if the sum of the received words (including checksum) is all 1s, no errors are declared. UDP provides error detection but not error correction.

Applications using UDP: DNS, streaming multimedia, SNMP, RIP. Applications that can tolerate some data loss but require speed. Advantages: finer application-level control, no connection establishment delay, no connection state, small packet header overhead (8 bytes vs. 20 bytes for TCP).

## 3.3 Principles of Reliable Data Transfer

Reliable data transfer over an unreliable channel is one of the most fundamental problems in networking. The service abstraction provided to the upper layer entities is that of a reliable channel through which data can be transferred.

**rdt1.0** assumes a perfectly reliable channel. The sender and receiver are simple FSMs that send and receive packets.

**rdt2.0** adds handling for bit errors via **ARQ (Automatic Repeat reQuest)** with three capabilities: error detection (checksum), receiver feedback (**ACK/NAK** — positive/negative acknowledgment), and retransmission. However, rdt2.0 has a fatal flaw: if an ACK/NAK is corrupted, the sender doesn't know what happened. **Stop-and-wait**: the sender sends one packet at a time and waits for receiver feedback before sending the next.

**rdt2.1** adds **sequence numbers** (0 or 1) to packets so the receiver can determine whether the received packet is a retransmission.

**rdt2.2** is a NAK-free protocol: instead of NAKs, the receiver sends an ACK for the last correctly received packet, adding the sequence number of the packet being ACK'd.

**rdt3.0** handles packet loss by adding a **timer**: after sending a packet, the sender starts a timer. If the timer expires before an ACK is received, the packet is retransmitted. Duplicate packets are handled by sequence numbers. rdt3.0 is also called the **alternating-bit protocol** (sequence numbers 0 and 1 alternate).

**Performance of stop-and-wait**: the sender utilization is:
\[U_{\text{sender}} = \frac{L/R}{RTT + L/R}\]
For a 1 Gbps link with 15 ms RTT and 8000-bit packets, \(U = 0.00027\) — a woeful 0.027%. **Pipelining** allows the sender to have multiple unacknowledged packets in transit, increasing utilization proportionally. Two general forms:

**Go-Back-N (GBN)**: the sender can have up to \(N\) unacknowledged packets in the pipeline (window size \(N\)). Sequence numbers require at least \(\log_2(N+1)\) bits. The receiver only accepts packets in order — any out-of-order packet is discarded. The receiver sends **cumulative ACKs**. If a timeout occurs, the sender retransmits packet \(n\) **and all** subsequently transmitted packets. This is the "go back N" behavior.

**Selective Repeat (SR)**: the sender can have up to \(N\) unacknowledged packets. The receiver **individually acknowledges** correctly received packets. Out-of-order packets are **buffered**. On timeout, only the specific unacknowledged packet is retransmitted. For SR, the window size must satisfy \(N \leq \text{sequence\_space} / 2\) to avoid ambiguity.

## 3.4 Connection-Oriented Transport: TCP

**TCP** provides a **connection-oriented**, **reliable**, **byte-stream** service with flow control and congestion control.

A **TCP segment** consists of a header of at least 20 bytes plus optional fields, and a data field. Key header fields:

| Field | Size | Description |
|-------|------|-------------|
| Source port | 16 bits | Sending port |
| Destination port | 16 bits | Receiving port |
| Sequence number | 32 bits | Byte offset of first data byte |
| Acknowledgment number | 32 bits | Next byte expected from other side |
| Header length | 4 bits | TCP header length in 32-bit words |
| Flags | 6 bits | URG, ACK, PSH, RST, SYN, FIN |
| Receive window | 16 bits | Used for flow control |
| Checksum | 16 bits | Error detection |
| Urgent data pointer | 16 bits | Used with URG flag |

TCP views data as an unstructured, ordered stream of bytes. TCP sets aside a **receive buffer** for each end of the connection. The **MSS (Maximum Segment Size)** limits the data portion of a TCP segment (typically 1460 bytes given an MTU of 1500).

**Sequence numbers** are byte-stream numbers of the first byte in the segment's data field. **Acknowledgment numbers** are the sequence number of the next byte the host is expecting. TCP provides **cumulative acknowledgments**.

**RTT estimation** uses an exponentially weighted moving average (**EWMA**):
\[\text{EstimatedRTT} = (1 - \alpha) \cdot \text{EstimatedRTT} + \alpha \cdot \text{SampleRTT}\]
with recommended \(\alpha = 0.125\). The **deviation** is:
\[\text{DevRTT} = (1 - \beta) \cdot \text{DevRTT} + \beta \cdot |\text{SampleRTT} - \text{EstimatedRTT}|\]
with recommended \(\beta = 0.25\). The **timeout interval** is:
\[\text{TimeoutInterval} = \text{EstimatedRTT} + 4 \cdot \text{DevRTT}\]

**TCP reliable data transfer**: the sender maintains a timer. Upon timeout, it retransmits the unacknowledged segment with smallest sequence number and restarts the timer. On receipt of three duplicate ACKs, **fast retransmit** allows the sender to retransmit the missing segment before the timer expires. TCP uses **cumulative acknowledgments** with a selective acknowledgment option (SACK).

**Flow control**: TCP provides flow control by having the sender maintain a **receive window** (rwnd). The receiver advertises its available buffer space in the rwnd field. The sender limits the amount of unacknowledged data to rwnd:
\[\text{LastByteSent} - \text{LastByteAcked} \leq \text{rwnd}\]

**TCP connection management**: a connection is established with a **three-way handshake**: (1) client sends SYN segment, (2) server responds with SYNACK segment, (3) client sends ACK. A connection is closed with a FIN-FINACK-FIN-FINACK four-step sequence (or a simultaneous close). The **TIME_WAIT** state ensures the final ACK reaches the server.

## 3.5 Principles of Congestion Control

**Congestion** arises when too many sources are sending too much data too fast for the network to handle, causing long queuing delays and packet loss. Two broad approaches:

**End-to-end congestion control**: no explicit feedback from network; congestion inferred from observed loss and delay (TCP's approach).

**Network-assisted congestion control**: network components provide explicit feedback to sender, e.g., a single-bit congestion indicator (**ECN — Explicit Congestion Notification**) or explicit rate.

The costs of congestion include large queuing delays and unnecessary retransmissions when packets are dropped. With multiple hops, congestion at one link causes upstream routers to waste transmission capacity on packets that will be dropped downstream.

## 3.6 TCP Congestion Control

TCP uses an **additive-increase, multiplicative-decrease (AIMD)** algorithm together with **slow start** and **congestion avoidance**.

TCP maintains a **congestion window (cwnd)** limiting the rate at which a TCP sender can send traffic:
\[\text{LastByteSent} - \text{LastByteAcked} \leq \min(\text{cwnd}, \text{rwnd})\]

**Slow start**: cwnd begins at 1 MSS and doubles every RTT (increases by 1 MSS per ACK received), growing exponentially. When cwnd reaches **ssthresh** (slow-start threshold), slow start ends.

**Congestion avoidance**: cwnd grows by 1 MSS per RTT (linear increase). On a loss event detected by a triple duplicate ACK, ssthresh is set to cwnd/2 and cwnd is set to ssthresh (TCP Reno). On a timeout event, ssthresh = cwnd/2 and cwnd = 1 MSS, entering slow start.

**TCP Reno** vs **TCP Tahoe**: TCP Tahoe sets cwnd to 1 MSS on both types of loss events (timeout and triple duplicate ACK). TCP Reno distinguishes: on triple duplicate ACK, it halves cwnd and enters congestion avoidance (fast recovery); on timeout, it resets cwnd to 1 and enters slow start.

The **TCP throughput** formula (ignoring slow start, simplified):
\[\text{average TCP throughput} = \frac{1.22 \cdot MSS}{RTT \cdot \sqrt{L}}\]
where \(L\) is the packet loss probability.

**TCP fairness**: if \(K\) TCP connections share a bottleneck link of bandwidth \(R\), AIMD leads all connections to converge to equal shares \(R/K\). This fairness result holds when all connections have the same RTT. In practice, connections with smaller RTT get disproportionately higher throughput.

**ECN (Explicit Congestion Notification)**: network routers set a bit in IP datagrams when congestion occurs. Receivers echo this via the ECE bit in TCP ACK segments, and senders halve cwnd as if a loss had occurred, without actual packet loss.

# Chapter 4: The Network Layer — Data Plane

## 4.1 Overview of Network Layer

The primary role of the network layer is to move packets from a sending host to a receiving host. Two important network-layer functions are **forwarding** (moving a packet from a router's input link to the appropriate output link, a per-router data-plane function taking nanoseconds) and **routing** (determining the route or path taken by packets as they flow from sender to receiver, a network-wide control-plane function taking seconds). **Flow tables** and **forwarding tables** link these two functions.

The **data plane** is the per-router function that determines how a datagram arriving on one of a router's input links is forwarded to one of its output links. The **control plane** is the network-wide logic that determines how a datagram is routed among routers along an end-to-end path (traditionally via routing algorithms in each router; alternatively via a logically centralized SDN controller).

In the **per-router control plane**, a routing algorithm runs in each router, with routing components in each router communicating with each other to compute forwarding tables. In the **Software-Defined Networking (SDN) control plane**, a logically centralized controller computes and distributes forwarding tables to routers.

The network layer in the Internet provides a best-effort service: packets may be lost, reordered, or delayed. No guarantees on bandwidth, loss, or delay.

## 4.2 What's Inside a Router

A router has four components: **input ports**, **switching fabric**, **output ports**, and a **routing processor**.

**Input ports** perform physical layer functions (receiving bits), link-layer functions, and the lookup function: given a packet's destination address, consult the forwarding table to determine the output port and forward the packet into the switching fabric. To handle high line rates, the forwarding table is cached in the input port memory. **Longest prefix matching** is used to match destination addresses to forwarding table entries — the entry with the longest matching address prefix wins.

**Switching fabrics** transfer packets from input ports to output ports. Three types: **switching via memory** (first-generation routers, CPU copies packets between I/O ports; bandwidth limited to \(B/2\) for \(B\) total backplane bandwidth), **switching via a bus** (packet transferred directly from input to output port over a shared bus; bandwidth limited by bus speed), and **switching via an interconnection network** (crossbar or multi-stage switching networks allowing multiple packets to be forwarded simultaneously).

**Output ports** store packets received from the switching fabric and transmit them on the outbound link. **Queuing** and packet scheduling are needed when packets arrive faster than they can be sent. **Head-of-line (HOL) blocking** occurs at input queues: a queued packet in an input queue must wait for transfer through the fabric even though its output port is free, because it is blocked by another packet at the head of the line going to a different congested output port.

**Packet scheduling** determines the order in which queued packets are sent: **FIFO** (first-in, first-out), **priority queuing** (highest-priority class served first), **round robin** (classes served cyclically), **weighted fair queuing (WFQ)** (generalized round robin with different weights per class giving different service rates).

## 4.3 The Internet Protocol (IP): IPv4, Addressing, IPv6

**IPv4 datagram format**: the header is 20 bytes (without options). Fields include:

| Field | Size | Description |
|-------|------|-------------|
| Version | 4 bits | IP version (4) |
| Header length | 4 bits | Header length in 32-bit words |
| Type of service | 8 bits | Differentiated services |
| Datagram length | 16 bits | Total length (header + data) in bytes |
| Identifier | 16 bits | Used for fragmentation |
| Flags | 3 bits | Fragmentation control |
| Fragmentation offset | 13 bits | Position of fragment |
| TTL | 8 bits | Time to live (decremented by each router) |
| Protocol | 8 bits | Transport protocol (6=TCP, 17=UDP) |
| Header checksum | 16 bits | Error detection |
| Source IP address | 32 bits | |
| Destination IP address | 32 bits | |

**IP fragmentation and reassembly**: links have a **maximum transmission unit (MTU)** which limits the largest IP datagram that can be sent on the link. Large datagrams are fragmented at intermediate routers into multiple smaller IP datagrams, each with the same identification number and an appropriate fragment offset and flag. Reassembly is performed only at the destination host.

**IPv4 addressing**: each host and router interface has an **IP address** — a 32-bit number. The boundary between each host/router and the physical link is called an **interface**. A subnet is a set of devices whose interfaces can physically reach each other without passing through an intervening router. The **subnet mask** (e.g., /24 in CIDR notation) indicates how many bits of the IP address define the subnet.

**CIDR (Classless Inter-Domain Routing)**: the Internet address assignment strategy. An IP address has the form a.b.c.d/x, where x indicates the number of bits in the network prefix. This replaced classful addressing (class A /8, class B /16, class C /24).

**DHCP (Dynamic Host Configuration Protocol)** allows a host to obtain an IP address automatically when it joins a network. It is a client-server protocol using UDP. The four-step interaction:
1. **DHCP discover**: newly arriving host broadcasts `255.255.255.255` on UDP port 67.
2. **DHCP offer**: server responds with an offered IP address and configuration.
3. **DHCP request**: client sends a request for the offered address.
4. **DHCP ACK**: server confirms and provides IP address, subnet mask, default gateway, and DNS server address.

**Network Address Translation (NAT)** allows a home/enterprise network to use private IP addresses internally, appearing to the outside world as having a single IP address. The **NAT translation table** maps (WAN-side IP, WAN-side port) to (LAN-side IP, LAN-side port). When a packet leaves the home network, NAT replaces the source IP/port; when a packet arrives, NAT uses the translation table to restore the original destination IP/port. NAT is controversial: it violates the end-to-end argument and treats port numbers as addressing information.

**IPv6** was developed to address the exhaustion of IPv4 address space. Key changes: **128-bit addresses** (providing \(2^{128}\) addresses), **fixed 40-byte header** (eliminating fragmentation, options moved to extension headers), **anycast address** (deliver to nearest of a group), no checksum in header (reduces processing at routers), **flow label** field.

IPv6 **tunneling**: since IPv6 deployment is incremental, IPv6 datagrams can be carried as the payload in IPv4 datagrams. The "tunnel" treats a sequence of IPv4 routers as a single link-layer network. The IPv6 datagram is encapsulated in an IPv4 datagram by the tunnel's entry router and decapsulated at the exit router.

## 4.4 Generalized Forwarding and SDN

In **generalized forwarding**, each router has a **flow table** computed and distributed by a logically centralized routing controller. Each entry has match fields (header values to match against), counters (updated for each matching packet), and actions (what to do: forward, drop, modify header, send to controller).

**OpenFlow** is a specific generalized forwarding protocol. Match fields in OpenFlow 1.0 include ingress port, Ethernet source/destination/type, IP source/destination/protocol, TCP/UDP source/destination port. Actions include forward to port(s), drop, modify-field (VLAN, TCP source port, IP destination, etc.), send-to-controller.

The power of SDN: **separation of the data plane** (packet forwarding) and **control plane** (routing decisions), **flow-based forwarding** (based on any combination of header fields), and **logically centralized control** with a programmable controller, enabling rapid innovation through software changes without touching hardware.

# Chapter 5: The Network Layer — Control Plane

## 5.1 Introduction

The network-layer control plane provides the per-router mechanism for determining how datagrams are routed among the routers along an end-to-end path. Two approaches: **per-router control** (traditional; routing algorithms run in each router) and **logically centralized control** (SDN; a centralized controller computes and distributes forwarding tables).

## 5.2 Routing Algorithms

A **routing algorithm** determines the best path from senders to receivers through the network of routers. The network can be modeled as a **graph** \(G = (N, E)\) where \(N\) is the set of nodes (routers) and \(E\) is the set of edges (links), each with a cost. The least-cost path between two nodes is the path such that the sum of link costs is minimum.

**Link-state (LS) routing**: each node broadcasts link-state packets containing link identities and costs to all nodes, so every node has an identical, complete view of the network graph. Dijkstra's shortest-path algorithm is then run locally. The algorithm is:

```
Initialize: D(v) = ∞ for all v ≠ u
            D(u) = 0
            S = {}
Loop:
    Find w not in S with minimum D(w)
    Add w to S
    For each neighbor v of w not in S:
        D(v) = min(D(v), D(w) + c(w,v))
Until all nodes in S
```

Complexity is \(O(N^2)\) with a naive implementation, \(O(N \log N)\) with a heap. A problem with LS routing is **oscillations**: if link costs depend on traffic volume, routes may oscillate as all routers simultaneously compute new routes after a traffic change.

**Distance-vector (DV) routing**: each node maintains a distance vector estimating the cost to every other node. Each node periodically sends its distance vector to its neighbors, and each node updates its estimates using the **Bellman-Ford equation**:
\[d_x(y) = \min_v \{ c(x,v) + d_v(y) \}\]
where the minimum is taken over all neighbors \(v\) of node \(x\). DV routing is **distributed**: each node only communicates with directly attached neighbors. It is **iterative**: the process continues until no more distance vector changes occur.

A key problem with DV routing is the **count-to-infinity problem**: when a link cost increases dramatically (or a link fails), it can take many iterations for the bad news to propagate. **Poisoned reverse** is a partial fix: if node \(z\) routes through \(y\) to reach \(x\), then \(z\) advertises to \(y\) that its distance to \(x\) is infinity.

**Comparison of LS and DV**:
- **Message complexity**: LS requires \(O(NE)\) messages; DV requires exchange only with neighbors.
- **Speed of convergence**: LS converges in \(O(N^2)\) algorithm steps; DV convergence is slower and subject to count-to-infinity loops.
- **Robustness**: LS — a node could broadcast an incorrect link cost, affecting only its own routing table. DV — a node can propagate erroneous distance estimates to all other nodes.

## 5.3 Intra-AS Routing in the Internet: OSPF

The Internet organizes routers into **Autonomous Systems (ASes)** — each AS consists of a group of routers under the same administrative control. Routers within the same AS run the same intra-AS routing protocol. Two most prevalent intra-AS routing protocols: **RIP (Routing Information Protocol)** using DV, and **OSPF (Open Shortest Path First)** using LS.

**OSPF**: a link-state protocol where each router constructs a complete topological map of the entire AS and then runs Dijkstra's to determine the shortest path tree. Topological information is flooded by sending OSPF **link-state advertisements (LSAs)** to all routers in the AS. OSPF is a publicly available protocol, the "O" in OSPF.

OSPF advantages: security (all OSPF messages authenticated), multiple same-cost paths (can use multiple simultaneously), support for unicast and multicast routing, hierarchical OSPF with **two-level hierarchy** (local area and backbone). A router in multiple areas is an **area border router**. **Backbone routers** run OSPF limited to the backbone. **Boundary routers** connect to other ASes.

## 5.4 Routing Among the ISPs: BGP

While intra-AS routing cares about performance, inter-AS routing is dominated by **policy** concerns: an AS may want to refuse to carry traffic between certain other ASes. **BGP (Border Gateway Protocol)** is the de facto standard inter-AS routing protocol — the "glue that holds the Internet together."

BGP provides each AS with the means to: (1) **obtain subnet reachability information** from neighboring ASes, (2) **propagate** the reachability information to all routers internal to the AS, (3) determine **good routes** to subnets based on reachability information and policy.

In BGP, pairs of routers exchange routing information over semi-permanent **BGP sessions** on TCP port 179. **eBGP** sessions span two ASes; **iBGP** sessions are between routers in the same AS.

BGP **route attributes** include **AS-PATH** (the list of ASes through which the advertisement has passed — used for loop detection and policy), **NEXT-HOP** (the IP address of the router interface that begins the AS-PATH). A **route** in BGP is a prefix plus attributes.

**Hot potato routing**: a router routes a packet toward the closest (least-cost, within the AS) NEXT-HOP router among multiple BGP-advertised paths, minimizing the cost within the AS, ignoring the inter-AS costs beyond the AS boundary. The router "gets rid of" the packet as quickly as possible.

**Route selection**: a BGP router uses several criteria in sequence: (1) highest **local preference** value (policy), (2) shortest AS-PATH, (3) closest NEXT-HOP router (hot potato), (4) BGP identifier as tiebreaker.

**IP-anycast** uses BGP to advertise the same IP address from multiple locations; the BGP shortest-path selection routes a client to the nearest server. Used by DNS and CDNs.

## 5.5 The SDN Control Plane

In an **SDN architecture**, the network's control-plane functions are moved to an external logically centralized controller. The controller communicates with the data-plane routers via a **southbound API** (e.g., OpenFlow). The controller receives data-plane state updates and computes flow-table entries to send to routers. Applications on top communicate with the controller through a **northbound API**.

The SDN controller architecture has three layers: (1) a **communication layer** implementing the southbound API to communicate with data plane devices, (2) a **network-wide state-management layer** maintaining the network graph, flow tables, and statistics, (3) the **northbound interface** toward network-control applications. Controllers such as OpenDaylight and ONOS implement these layers.

**OpenFlow protocol** operates between the controller and a switch, using TCP (optionally TLS). Messages: controller-to-switch (flow modification, read state, send-packet), switch-to-controller (packet-in when no match, flow-removed, port status), and symmetric (hello, echo request/reply).

## 5.6 ICMP: The Internet Control Message Protocol

**ICMP (Internet Control Message Protocol)** is used by hosts and routers to communicate network-level information, primarily error reporting. ICMP messages are carried in IP datagrams (protocol number 1). An ICMP message has a type, code, and the first 8 bytes of the triggering IP datagram.

Common ICMP message types include: echo request (type 8)/echo reply (type 0) used by `ping`; destination unreachable (type 3, various codes for host unreachable, port unreachable, etc.); source quench (type 4, deprecated congestion control); time exceeded (type 11, used by traceroute).

**Traceroute** works by sending UDP segments (or ICMP echo requests) with incrementally increasing TTL values, starting at 1. Each router that decrements TTL to 0 returns an ICMP "time exceeded" message, revealing the router's IP address. By sending a final datagram to an unlikely port, the destination host returns an ICMP "port unreachable" message, indicating the destination has been reached. The round-trip time for each hop is measured.

# Chapter 6: The Link Layer and LANs

## 6.1 Introduction to the Link Layer

The **link layer** is responsible for transferring a datagram from one node to an **adjacent** node over a single communication link. This is contrast to the network layer, which provides end-to-end logical communication. Link-layer services include: **framing** (encapsulating a network-layer datagram in a link-layer frame), **link access** (a MAC protocol coordinates frame transmissions on shared medium), **reliable delivery** (guaranteed delivery over the link, often used for high-BER wireless links), **error detection and correction** (hardware-implemented).

The link layer is implemented in a **network adapter** (also called a **network interface controller, NIC**), which is a combination of hardware, software, and firmware. The adapter attaches to the host's system bus; most of the link-layer functionality is implemented in hardware.

## 6.2 Error-Detection and Correction Techniques

**Parity bits**: a single parity bit allows detection of any odd number of bit errors. A two-dimensional parity scheme can both detect and correct single-bit errors.

**Checksum**: the bytes of the data are treated as 16-bit integers and summed. The 1s-complement of the sum forms the checksum. Checksums are used in the Internet (IP, UDP, TCP).

**Cyclic Redundancy Check (CRC)**: more powerful error-detection technique. The sender and receiver agree on a \(r+1\)-bit **generator** polynomial \(G\). The sender appends \(r\) CRC bits to the \(d\)-bit message such that the resulting \(d+r\)-bit pattern is exactly divisible by \(G\) using modulo-2 arithmetic. The receiver divides the received \(d+r\) bits by \(G\); if the remainder is non-zero, an error is detected. CRC can detect all burst errors of fewer than \(r+1\) bits. Used in Ethernet, WiFi, ATM.

## 6.3 Multiple Access Links and Protocols

Communication links are either **point-to-point** (a single sender and receiver at each end) or **broadcast** links (multiple sending and receiving nodes connected to the same shared broadcast channel). Multiple nodes transmitting on a broadcast channel simultaneously causes a **collision**.

**Multiple access protocols** coordinate transmissions on a shared broadcast channel. Three broad classes:

**Channel partitioning protocols**: divide the channel into pieces — **TDMA (Time-Division Multiple Access)** allocates time slots, **FDMA (Frequency-Division Multiple Access)** allocates frequency bands. Fair and avoids collisions, but wastes capacity when fewer than N nodes are active.

**Random access protocols**: a node always transmits at full rate \(R\); on a collision, nodes retransmit after random delays.

- **Slotted ALOHA**: all frames are \(L\) bits; time is divided into slots of \(L/R\) seconds. A node transmits at the beginning of a slot; if collision, retransmit in subsequent slot with probability \(p\). Maximum efficiency is \(1/e \approx 0.37\).
- **Pure (unslotted) ALOHA**: simpler (no synchronization required). Maximum efficiency is \(1/(2e) \approx 0.18\).
- **CSMA (Carrier Sense Multiple Access)**: listen before talking. If channel idle, transmit; if busy, defer. Collisions still occur due to **propagation delay**.
- **CSMA/CD (CSMA with Collision Detection)**: transmitting nodes also listen while transmitting; on detecting collision, abort transmission. Used in Ethernet. Efficiency: \(\text{efficiency} = 1 / (1 + 5d_{\text{prop}} / d_{\text{trans}})\).

**Taking-turns protocols**: **polling** — a master node polls each node in round-robin fashion; **token passing** — a special-purpose frame called a token is passed from node to node; a node can transmit only when holding the token. Taking-turns eliminates collisions and empty slots but introduces latency and failure points.

## 6.4 Switched Local Area Networks

**MAC addresses** (also called **LAN addresses** or **physical addresses**) are 48-bit identifiers (6 bytes), typically written in hexadecimal (e.g., `1A-23-F9-CD-06-9B`). MAC addresses are flat — they don't change based on location. The broadcast MAC address `FF-FF-FF-FF-FF-FF` reaches all adapters on the LAN. IEEE manages the MAC address space; organizations buy blocks of \(2^{24}\) addresses.

**ARP (Address Resolution Protocol)** translates IP addresses to MAC addresses within a subnet. Each host and router has an **ARP table** mapping IP addresses to MAC addresses (with TTLs). To find the MAC address for an IP address, a host broadcasts an ARP query packet containing the target IP; the node with that IP responds with its MAC address. ARP is plug-and-play.

## 6.5 Ethernet

Ethernet is by far the most widely used wired LAN technology. The original bus-topology Ethernet used CSMA/CD with a shared coaxial cable; today, Ethernet is typically used with switches in a **star topology**.

**Ethernet frame structure** (minimum 64 bytes, maximum 1518 bytes):

| Field | Size | Description |
|-------|------|-------------|
| Preamble | 7 bytes | `10101010...` for clock synchronization |
| SFD | 1 byte | `10101011` — start frame delimiter |
| Destination MAC | 6 bytes | |
| Source MAC | 6 bytes | |
| Type/Length | 2 bytes | Network-layer protocol (e.g., 0x0800 for IP) |
| Data (payload) | 46–1500 bytes | Network-layer datagram |
| CRC | 4 bytes | Error detection |

Ethernet is **connectionless** (no handshaking) and **unreliable** (dropped frames not retransmitted by Ethernet itself — higher-layer protocols handle this). Ethernet's MAC protocol is CSMA/CD with **binary exponential backoff**: after the \(n\)th collision, the node waits a random number of slots from \(\{0, 1, \ldots, 2^n - 1\}\) before retransmitting. After 10 collisions the range freezes at 1023 slots; after 16 consecutive collisions the adapter gives up.

## 6.6 Link-Layer Switches

A **link-layer switch** (also simply **switch**) receives incoming link-layer frames and forwards them to outgoing links. Switches are **transparent** to hosts and routers — they see no change in operating.

**Self-learning**: a switch's forwarding table is built automatically as follows. For each incoming frame, the switch records (1) the MAC address in the frame's source address field, (2) the interface from which the frame arrived, and (3) the current time. If the destination is in the table, forward to the designated interface; if not, **flood** (forward to all interfaces except the arriving one). Entries are deleted after an **aging time**.

Switches vs. routers: both are store-and-forward devices. Switches are layer-2 devices operating on MAC addresses; routers are layer-3 devices operating on IP addresses. Switches are plug-and-play but are susceptible to broadcast storms; routers provide more robust isolation.

**VLANs (Virtual Local Area Networks)** allow a single switch (or interconnected switches) to be configured to operate as if it were multiple disjoint switches. Ports are grouped into VLANs; frames from one VLAN cannot cross to another without going through a router. This provides traffic isolation, dynamic membership, and efficient use of switch hardware.

## 6.7 Retrospective: A Day in the Life of a Web Page Request

Consider what happens when a student opens a laptop in a university network and browses to `www.google.com`. This scenario ties together all the layers of the protocol stack.

**DHCP**: the laptop broadcasts a DHCP discover message within a UDP datagram. The nearest router (which also acts as DHCP server) sends back a DHCP ACK with IP address, subnet mask, default router IP, and local DNS server IP. The laptop's OS records these.

**ARP and the first-hop router**: to send a DNS query to the local DNS server, the laptop first needs the MAC address of the default router. It sends an ARP query; the router replies with its MAC address, which the laptop caches.

**DNS**: the laptop creates a DNS query for `www.google.com` and sends it via UDP to the local DNS server. The local DNS server contacts the root DNS servers, then the TLD `.com` server, then Google's authoritative DNS server, returning the IP address.

**TCP and HTTP**: with the IP address, the laptop initiates a TCP connection (3-way handshake) to Google's server at port 80. An HTTP GET request is sent over the connection. The HTTP response returns the web page content. The browser renders the page, making additional HTTP requests for embedded objects.

Throughout this journey, every packet carries multiple header layers: Ethernet frame at the link layer, IP datagram at the network layer, TCP segment at the transport layer, HTTP message at the application layer — all wrapped in each other by encapsulation.
